# outbox

Транзакционный outbox поверх PostgreSQL: задание пишется в ту же транзакцию,
что и бизнес-операция, а отправляет его фоновый воркер.

## Нужен ли он вам

Не всегда. Вопрос, на который стоит ответить до подключения: *что случится,
если задание потеряется?*

| Потеря | Пример | Решение |
|---|---|---|
| Пользователь заперт | код входа, подтверждение почты | outbox |
| Пользователь не узнал приятного | «вы сменили имя», приглашение, которое и так видно в приложении | прямой вызов |

Во втором случае таблица и воркер не окупаются: достаточно вызвать сервис
доставки напрямую и записать warn в лог при неудаче.

## Подключение

Миграция едет вместе с пакетом и накатывается **своей** таблицей версий —
у goose одна линейная история на таблицу, и два набора в общей истории он
сочтёт чужими версиями:

```go
_, err := migrate.Up(ctx, cfg.Postgres, outbox.Migrations, migrate.Config{
	Dir:    "migrations",
	Table:  "outbox_migrations",
	Logger: log,
})
```

Дальше репозиторий, свой Sender и воркер в runner:

```go
queue := outbox.NewRepository(pool)

components := runner.New(log).
	Add("outbox", outbox.NewWorker(cfg.Outbox, queue, sender, log).Run)
```

## Постановка задания

`Enqueue` принимает то, в чём идёт бизнес-операция, — транзакцию. В этом
весь смысл: задание обязано появиться ровно тогда, когда коммитится то,
из-за чего оно возникло.

```go
err := postgresql.InTx(ctx, pool, func(tx pgx.Tx) error {
	user, err := createUser(ctx, tx, email)
	if err != nil {
		return err
	}

	payload, err := json.Marshal(emailJob{To: user.Email, Code: code})
	if err != nil {
		return err
	}

	_, err = outbox.Enqueue(ctx, tx, "email", payload, 5)

	return err
})
```

Возвращённый `Enqueue` идентификатор устойчив и годится принимающей стороне
как ключ идемпотентности: повтор доставки придёт с тем же значением.

## Sender

Пакет не знает, что лежит в `Payload`, — это знает сервис:

```go
func (s *emailSender) Send(ctx context.Context, m outbox.Message) error {
	var job emailJob
	if err := json.Unmarshal(m.Payload, &job); err != nil {
		// Разобрать не удалось и не удастся — повторять нечего.
		return outbox.Terminal(err)
	}

	return s.client.SendEmail(ctx, m.ID, job)
}
```

### Временные ошибки и окончательные

По умолчанию ошибка считается временной: воркер повторяет её с удвоением
паузы от `BaseBackoff` до `MaxBackoff`, пока не кончится `max_attempts`.
Так и надо для сети, таймаутов и «сервис перезагружается».

Ошибку, повтор которой ничего не изменит — неизвестный тип, битый payload,
отвергнутый получатель, — оберните в `outbox.Terminal`. Такое задание
гаснет с первой попытки и не занимает очередь пятью бесполезными подходами.

## Как это работает

Захват идёт через `FOR UPDATE SKIP LOCKED`, поэтому две реплики не возьмут
одну строку. Блокировка снимается вместе с коммитом захвата, а не держится
всю отправку — внешний вызов медленный, и держать на нём строчную
блокировку нельзя.

Роль «взято в работу» играет `next_attempt_at`, сдвинутый вперёд на
`VisibilityTimeout`. Если воркер умрёт с заданием в руках, оно вернётся в
очередь само, когда таймаут истечёт.

Успешная отправка **удаляет** строку: в payload может лежать то, что не
должно её пережить, — например код подтверждения в открытом виде. По той же
причине outbox не стоит включать в бэкапы.

Провалившиеся строки, наоборот, остаются: по ним разбираются, что сломалось.
Убирает их `DeleteOldFailed` по `FailedRetention`, воркер зовёт её сам раз в
`CleanupInterval`.

## Настройки

Все с префиксом на усмотрение сервиса (`envPrefix:"OUTBOX_"`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `POLL_INTERVAL` | `2s` | пауза, когда очередь пуста |
| `BATCH_SIZE` | `20` | заданий за проход; полная пачка означает продолжение без паузы |
| `VISIBILITY_TIMEOUT` | `2m` | через сколько зависшее задание вернётся в очередь |
| `SEND_TIMEOUT` | `30s` | дедлайн одной отправки; держите заметно меньше видимости |
| `BASE_BACKOFF` | `30s` | пауза после первой неудачи |
| `MAX_BACKOFF` | `30m` | потолок паузы |
| `FAILED_RETENTION` | `168h` | сколько хранить провалившиеся |
| `CLEANUP_INTERVAL` | `1h` | как часто их убирать |

## Тесты

Юнит-тесты гоняют воркер на подставной очереди и базы не требуют.
Проверка SQL на живой PostgreSQL включается переменной:

```bash
OUTBOX_TEST_DSN="postgres://postgres:p@localhost:5432/t?sslmode=disable" go test ./outbox/
```
